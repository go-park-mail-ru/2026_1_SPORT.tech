# Нагрузочное тестирование БД

Основная сущность приложения - **пост** (`content_post` в сервисе `content`).

| Действие | Endpoint | Что делает в БД |
|----------|----------|-----------------|
| создание | `POST /v1/posts` | транзакция: `INSERT` в `content_post` + `content_post_block`, затем чтение созданного поста и рассылка уведомлений |
| чтение | `GET /v1/posts/{post_id}` | один `SELECT` поста с агрегатами (лайки, комментарии, виды спорта) + `SELECT` блоков |

Инструмент - vegeta.

Генератор `./gen_targets.py`

## Что тестируется

Тестируем напрямую в `content-service` (`:8083`).

`init.sql` - исходный DDL базы `sporttech_content` (схема до каких-либо оптимизаций).
## Стенд

Всё поднимается в Docker.

- `db` - PostgreSQL 17, пул приложения 12 соединений (`db_max_open_conns: 12`),
  `statement_timeout = 5s` у сервисного пользователя;
- `content-service` - Go, HTTP-gateway на `:8083`;
- нагрузка и сервис крутятся на одной машине.

## Как воспроизвести

```bash
# поднять приложение (db + content-service)
bash perf_test/run.sh up

# сгенерировать таргеты, наполнить базу до 100k постов, прогнать чтение
bash perf_test/run.sh gen
bash perf_test/run.sh create      # POST /v1/posts до 100 000 постов
bash perf_test/run.sh read        # GET  /v1/posts/{id}

# вспомогательное
bash perf_test/run.sh stats       # размеры таблиц, число постов
bash perf_test/run.sh reset       # TRUNCATE content_post
bash perf_test/run.sh down        # закрыть приложение
```

Параметры через переменные окружения: `TARGET`, `CREATE_RATE`, `READ_RATE`,
`READ_DURATION`. Например, прогон записи был сделан с `CREATE_RATE=500`.

Отчёты vegeta складываются в `perf_test/results/`

## Итерация 1 — запись (`POST /v1/posts`)

Создаём 100 000 постов. Перед тестом в базе было 12 постов.

**Параметры:** rate 500 rps, 200 c, 100 000 запросов.

```
Requests      [total, rate, throughput]         100000, 500.00, 499.99
Latencies     [min, mean, 50, 90, 95, 99, max]  2.017ms, 4.46ms, 3.527ms, 7.234ms, 11.919ms, 15.013ms, 157.203ms
Success       [ratio]                           100.00%
Status Codes  [code:count]                      200:100000
```

Итог: в базе 100 012 постов и 100 034 блока. Размеры таблиц после наполнения:

```
content_post_block   37 MB
content_post         20 MB
```

**Вывод:** запись держит 500 rps без единой ошибки, средняя задержка 4.46 мс,
p99 = 15 мс.
То есть на нашем объёме запись в узкое место не упирается

500 rps бралось как "рабочая" нагрузка.

## Итерация 2 — чтение (`GET /v1/posts/{id}`)

База уже наполнена на 100к постов. Читаем по случайным `post_id` из диапазона.

Базовый прогон: rate 1000 rps, 30 c, 30 000 запросов.

```
Requests      [total, rate, throughput]         30000, 1000.01, 982.41
Latencies     [min, mean, 50, 90, 95, 99, max]  517.332µs, 1.085ms, 1.041ms, 1.414ms, 1.511ms, 1.777ms, 3.971ms
Success       [ratio]                           98.24%
Status Codes  [code:count]                      200:29473  403:5  404:522
```

- `404` (~1.7%) - случайные `id` из "дыр" в диапазоне (id 1..2000 не существуют);
- `403` — несколько закрытых сид-постов с `required_subscription_level`;
  это не ошибки нагрузки, а нормальная бизнес-логика.

### Предел нагрузки

Чтобы найти потолок, прогон чтения на 2000 / 4000 / 8000 / 12000 rps по 15 c:

| Запрошено rps | Реальный throughput | mean | p99 | success | ошибки |
|---------------|--------------------:|-----:|----:|--------:|--------|
| 2 000  | 1 965  | 0.89 ms | 1.95 ms | 98.2% | — |
| 4 000  | 3 929  | 0.88 ms | 1.70 ms | 98.2% | — |
| 8 000  | 2 991  | **4.25 s** | 9.97 s | 89.7% | 4 870 (conn) |
| 12 000 | 69     | **5.20 s** | 13.3 s | 3.6%  | 40 352 (conn) |

До ~4000 rps - стабильно ~1 мс, throughput линейно растёт.
На 8000 rps система резко ломается: throughput падает до ~3000, задержки
взлетают с миллисекунд до секунд, появляются ошибки соединений.
На 12000 rps - все плохо :(

## Анализ (что является узким местом)

### SQL-запрос

`EXPLAIN (ANALYZE, BUFFERS)` запроса `GetPost` для `post_id = 50000`

```
Nested Loop Left Join (actual time=0.096..0.098 rows=1)
  Buffers: shared hit=13
  ->  Index Scan using content_post_pkey on content_post p
        Index Cond: (post_id = 50000)
  ->  GroupAggregate
        ->  Bitmap Heap Scan on content_post_like
              Recheck Cond: (post_id = 50000)
  ->  GroupAggregate
        ->  Bitmap Heap Scan on content_comment
              Recheck Cond: (post_id = 50000)
```

По первичному ключу чтение одного поста эффективно.

### Пул соединений + один хост

Деградация на 8000 rps наступает не из-за плана запроса , а из-за
конкуренции за пул из 12 соединений к БД. Каждый `GetPost` — это 2 обращения к базе
(основной запрос + выборка блоков). Когда входящий поток превышает то, что 12 соединений
успевают обслужить, запросы встают в очередь.

### Что можно улучшить

1. Увеличить пул соединений `db_max_open_conns`. Также можно поставить pgbouncer.
2. Схлопнуть 2 запроса в 1. Блоки поста сейчас читаются отдельным `SELECT`.
   Их можно достать тем же запросом через `json_agg`/`array_agg` подзапросом.
